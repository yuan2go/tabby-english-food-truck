# 产品文档 · 狸花猫的英语餐车

版本：v0.2，2026-09-20。本轮 M1 明确包含三层渐进玩法；下文完整首包的吐司、拼写与场次仍是有效后续设计，不代表本轮扩展授权。

已确认：负责人选择餐车方向并建立独立仓库 `yuan2go/tabby-english-food-truck`。本文中的场次、语言材料、容量和时间属于设计提案，不代表已实现、已教研审核或已证明好玩。玩法细则见 [02](02-game-design.md)，当前状态见 [STATUS](STATUS.md)。

## 1. 产品定义

中文名：狸花猫的英语餐车。英文名：Tabby's English Food Truck。仓库名：tabby-english-food-truck。可在提交材料中注明属于“雪梨英语奇旅”的独立参赛作品，但不继承旧应用，也不宣称已接入公司其他产品。

产品是单人、触控优先、以连续服务为核心的二维网页游戏。孩子是柜台主厨，狸花猫是取料与接待助手；理解客人的英语请求，准备食物，安排设备与托盘，再交给正确客人。

不是英语练习网页、烹饪教学软件、餐厅经营后台或小游戏合集。餐车是玩具化场景，不提供真实儿童使用热源/刀具的操作指导。

## 2. 三个必须同时成立的支柱

**做事情有手感。** 食材拿得起、放得下，机器有输入、过程和成品，交付有角色回应。动作在场景中连续发生，而不是提交表单后换一张图片。

**安排事情有选择。** 苹果汁加工时可以准备水果或吐司；两个托盘和设备出口不能无限堆物。不同安排影响等待和返工，但默认不靠顾客生气、限时失败制造压力。

**英语有实际用途。** 请求决定需要什么、多少和哪种组合；给小猫的便签可以改变取料行动。英语并非随便回答一道题后换取行动许可。

任何一项不成立，都不能仅凭功能齐全或引擎已接入就扩建。

## 3. 目标玩家与支持

本轮目标为 3–6 岁儿童，不以识字、拼读或完整句子理解为开始条件；年龄不作为自动定级依据。首次体验允许完全不会餐车词汇的孩子通过演示继续，但不能将有支持完成记录为独立能力。

语言难度和服务难度独立：新词出现时保持单客与低操作负荷；熟悉后再增加数量、组合及双客。成人/评委可以直接体验，不强制注册、选年级或观看长说明。

主要设备为手机竖屏、Pad 触控；桌面鼠标与键盘提供等价路径。目标网络环境和设备性能须实际测量，不宣称自动适配所有浏览器。

## 4. 玩家流程

启动与声音选择 → 开店前短教学/备料 → 连续服务 → 场次结束的短场景反馈 → 下一场或重玩。

有未完成场次时明确提供继续和重新开始。教学与复习从餐车小食谱入口进入，不在主屏并列展示课程树、工坊、词语册和统计面板。暂停界面可看简短本地学习记录。

第一局应尽快让玩家完成一次自己发起的拿取与交付。首分钟形成可理解操作是设计目标，不是已测转化率或留存承诺。

## 5. 首版范围

| 能力 | 首版要求 | 明确边界 |
| --- | --- | --- |
| 场景 | 一辆完整餐车、一套可读柜台和昼间集市场景 | 不做自由行走地图、多个餐厅或换场景拼贴 |
| 服务 | 水果直接装盘、苹果汁加工、面包烘烤三条流程 | 不做复杂菜单、调味系统和真实烹饪模拟 |
| 容量 | 两位并发客人、两个托盘、每托盘三份成品容量 | 入门场次单客；第三客仅排队背景，不发布隐形订单 |
| 伙伴 | 小猫有接待与取料任务；动作影响实际供料 | 不做多人、语音聊天或自主完成整单的 AI |
| 语言 | 意义学习、听请求、数量/组合、便签组词句、备料拼写、回访 | 不强迫每次取料先拼写，不承诺完整英语课程 |
| 内容 | 三个短场次和一个变体回访 | 数量约束首个内容包，不写死为全局产品限制 |
| 保存 | 本地继续、设置、帮助/尝试记录和明确重开 | 不迁移旧项目存档、不建账号与云同步 |
| 发布 | HTTPS 可玩地址、简短设计说明、真实 AI 制作记录 | GitHub 链接不是试玩地址；公开发布须另验收 |

体验目标为每场约 3–5 分钟，但玩家慢想不会被强制结束。具体时长根据试玩调整，不能为凑时长增加机械点击。

## 6. 学习设计

### 6.1 首包语言范围

食品/成品：apple、banana、bread、toast、apple juice。器具辅助词：cup、tray。数量：one、two。结构涉及 a/an、复数 -s、and、please。多词短语不拆分虚增词汇覆盖量。

候选请求：An apple, please. / A banana, please. / Two apples, please. / An apple and a banana, please. / Apple juice, please. / Apple juice and toast, please.

这些自然场景请求包含省略表达，不一律当“语法不完整”。toast/juice 不直接套用可数名词复数；菜单约定 toast 是一片、apple juice 是一杯，首次明确说明。首版不要求 two toasts 或 two juices 作为基础标准答案。所有用语、图像指代与音频仍须教研审核。

### 6.2 学习序列

先用物品、声音和动作表达意义，再进行辅助操作；随后在关闭泄露答案的支持后进行独立条件尝试；最后在换客人、顺序和组合的场次中回访。重听不处罚，不自动算作泄露答案。

模式是活动上下文，不是永久儿童等级：引导学习、辅助练习、独立练习、复习回访分别标记。进入独立条件不剥夺帮助按钮；点帮助后继续游戏，并改变本次证据口径。

### 6.3 不把服务速度当英语水平

语音请求成功交付最多作为听力/语义应用的一次观察；手速、设备等待和托盘整理单独记录为操作。看过目标图片/文字后完成属于相应支持条件。拼字成功不自动证明听懂单词，句型正确不自动证明订单已满足。

不收集发音评分，不调用麦克风。没有真实数据不显示“掌握率”“提升百分比”或正式测评结论。

## 8. 进度与奖励

当前场次以完成有限订单结束，订单可以换序处理。场次标记仅表示服务进度，不代表语言掌握。奖励以客人反应、餐车短纪念画面和下一场需求变化为主；不建金币、抽卡、签到、全球排行榜或付费成长。

带速度压力的额外“熟练模式”只属后续范围；本轮“小小餐车营业中”已是必须实现的第三层，仍无速度惩罚。默认版不用总时限、烧焦、食物变质或客人离开惩罚。操作效率可在场后作为自我观察，不进入学习评分。

## 9. 非目标

不做账号、课程后台、支付、广告、社交、多人、房间、复杂经营、自由聊天、在线判题模型、自动语音评分、万能编辑器、无限配方或旧档兼容。不开另一组战斗/冒险/跑酷玩法。

不需要为赢取比赛而收集儿童数据或暴露公司素材。活动时间与验收要求来自负责人提供的说明；文档不包含公司未公开材料、内部接口或奖项保证。

## 10. 成功假设与观察方法

H1：玩家基本引导后知道下一步能做什么。观察停顿原因，不只记录完成时长。

H2：双订单下会出现主动启动机器、利用等待时间或腾盘的行为。机械照箭头点击不算该假设成立。

H3：没有永久答案卡时，目标语言仍参与选择；改变客人外观/位置后不能只靠记位置通关。

H4：玩家完成后愿意再尝试一个订单组合，或能说出自己会调整的顺序。

由负责人先确认视觉/手感，再在适当监护条件下做小范围儿童观察。记录支持程度、卡点与退出原因；小样本不推导学习效果或普遍吸引力。具体完成标准见 [05](05-delivery.md)。

## 11. AI 与素材边界

AI 可辅助制作角色/场景草稿、动画方案、音频候选、英语内容候选和代码；人工审查通过后才进入内容包。保留使用工具、任务、输出位置、人工修改和审核状态。不伪造使用日志，不将规则调度营销成运行时 AI。

核心游戏无在线模型依赖。语音优先预生成并听审；无审核资源时可开发降级但不伪造发布资格。角色、声音、字体和素材各有来源记录，代码许可证不能替代素材许可。

## 12. 新仓库原则

从空白应用和本文件开始。旧项目玩法/UI 不作为比较目标、代码基线或兼容需求。确认的狸花猫设定可以延续，素材按新构图与动作需求重新制作或逐件审核；没有自动搬运许可。

GitHub 仓库已存在不代表已经开发或部署。开发阶段采用独立分支与 PR；不因文档可读就标游戏完成。
